# DECISIONS — <模组名>

## D-001 目标平台锁定 Minecraft 1.20.1 + Forge 47.x

- **背景**：新项目要跑在 1.20.1。
- **决定**：`mappings channel: 'official', version: '1.20.1'`，Forge `47.x`。
- **后果**：1.20.1 之后 Forge 不再提供（1.20.2+ 官方转向 NeoForge），平台到此为止。
  升级等于换生态，不是改版本号。

## D-002 Java 17 + Gradle 8.x

- **背景**：1.20.1 用 Java 17 编译；ForgeGradle 6 需要 Gradle 8.x。
- **决定**：`.build-tools/jdk17` + `bootstrap_toolchain.py` 拉 Gradle 8.5。
- **后果**：旧项目的 Gradle 7.3/7.6 不能用于新项目，别再拷过来。

## D-003 依赖走本地 Python Maven 镜像

- **背景**：Gradle 走本地 VPN 代理时 TLS 握手失败，Python urllib 不会。
- **决定**：`tools/local_maven_proxy.py` 在 `127.0.0.1:8765` 提供纯 HTTP 镜像，
  build.gradle 的仓库指向它的 `/forge/`、`/central/`、`/mojang/`、`/sponge/` 前缀。
- **后果**：构建前必须先起这个进程；它是唯一走得通的依赖通道。

## D-004 继承旧项目的工具链，不继承代码

- **背景**：上一个 1.18.1 项目（Void Star）已完成，工具链和排障经验可复用，代码不兼容。
- **决定**：`tools/` 和 `docs/COMMANDS.md` 的排障部分搬过来；Java 源码、资源、
  `build.gradle`、手工编译参数一律重写。
- **后果**：遇到类似机制可以回旧项目查"当时怎么写的"，但不要复制类文件。

## D-005 构建 JVM 用 JDK 21，mod 字节码保持 Java 17

- **背景**：项目自带 JDK 17.0.20.1 在本机 Windows 沙箱里，`Files.isWritable()` 对 Java 自己刚创建的文件
  返回 `false`；zipfs 因此把新 jar 以只读打开，ForgeGradle 的 AccessTransformer 必抛
  `ReadOnlyFileSystemException`。同一程序在系统 JDK 21 下正常。
- **决定**：Gradle 与 `java.toolchain.languageVersion` 用 JDK 21，
  `JavaCompile.options.release = 17` 保证 mod class 仍是 Java 17 字节码。
- **后果**：构建机必须有 JDK 21；JDK 17 不再是构建 JVM。换到没有该 zipfs 行为的环境后可以改回 17。

## D-006 关闭 ForgeGradle 的 Forge Maven 证书检查

- **背景**：本地代理/证书链下，ForgeGradle 在 `apply plugin` 时校验
  `https://maven.minecraftforge.net/` 证书失败。
- **决定**：`org.gradle.jvmargs` 加 `-Dnet.minecraftforge.gradle.check.certs=false`。
- **后果**：依赖仍全部走本地镜像（见 D-003），这个检查对实际下载没有保护作用。

## D-007 每个模组一个顶层目录，工具链与缓存共享

- **背景**：同一工作区后续会有多个模组，不能把 `build.gradle` / `src` / `docs` 混在根目录。
- **决定**：`inscribe/` 放该模组的全部工程文件；`.build-tools/`、`.gradle-home/`、`tools/` 留在工作区根共享。
- **后果**：在 `inscribe/` 下执行 Gradle，共享路径写成 `../`；新模组同级建目录，不复制工具链。

## D-008 可复用数据统一放 shared/

- **背景**：D-007 之后工具链仍散在根目录（`.build-tools/`、`.gradle-home/`、`tools/`），和模组目录混在一起。
- **决定**：三者整体移入 `shared/`；`inscribe/` 只保留自己的 `build.gradle` / `src` / `docs` / `build`。
- **后果**：命令从 `inscribe/` 用 `../shared/...`；`tools/` 脚本的 `parents[1]/.build-tools` 正好解析到 `shared/.build-tools`，脚本无需改。

## D-009 远及附魔用 ENTITY_REACH 临时属性修饰器

- **背景**：1.20.1 的攻击距离由 `ForgeMod.ENTITY_REACH` / `IForgePlayer#getEntityReach()` 驱动，
  客户端准星和服务端校验都要认；不能用单纯的伤害事件改距离。
- **决定**：服务端 `PlayerTickEvent` 的 END 阶段检查主手附魔等级，给 `ENTITY_REACH` 添加/更新/移除
  固定 UUID 的 transient `ADDITION` 修饰器；客户端通过属性同步获得同一数值。
- **后果**：换手、死亡、维度切换由 tick 自动纠正；不要改成 permanent 修饰器，否则会写进玩家数据。

## D-010 远及默认获取率

- **背景**：需求只给了来源，没有给交易价格/掉落概率。
- **决定**：图书管理员专家 20–32 绿宝石、3 次；钓鱼 2%；古城 10%；末地城 15%；
  宝箱内 I:II = 3:1；附魔台不出。
- **后果**：这些都是平衡参数，集中在 `OutreachEvents`；调整只改常量，不改结构。

## D-011 构建不再使用 Sponge 仓库

- **背景**：`repo.spongepowered.org` 经 7890 返回 WinError 10061；Forge maven 已代理 modlauncher / Mixin。
- **决定**：`build.gradle` 只保留 `/forge/`、`/central/`、`/mojang/`，删除 `/sponge/`。
- **后果**：当前 1.20.1 构建已验证可用；若将来有仅发布在 Sponge 的依赖，需要恢复并解决上游。

## D-012 远及加入附魔台 30 级档

- **背景**：补充需求：附魔台也能获得，要求满级附魔台、在 30 级档位出现。
- **决定**：`canApplyAtEnchantingTable` 仅剑/斧；`getMinCost(1)=30`、`getMinCost(2)=45`。
  满级 15 书架时第三档成本为 30/31，因此只出 I 级；成本 29 及以下不出。
- **后果**：覆盖 D-010 里“附魔台不出”的部分；II 级仍靠铁砧/宝箱/交易。
  如果以后要让 II 级也在 30 档出现，把 level 2 的 minCost 降到 30 即可。

## D-013 再跃用客户端按键包 + 服务端校验

- **背景**：服务端默认收不到“空中按下跳跃”这个输入；二段跳又必须由服务端授权速度，否则移动会被拉回。
- **决定**：客户端 `InputEvent.Key` 检测跳跃键按下且滞空时，发一个空 `SimpleChannel` 包；
  服务端校验靴子附魔、滞空、未用过、非水域/骑乘/鞘翅/飞行/旁观/攀爬/死亡后，
  设置二段速度（I=0.42、II=0.58）、重置坠落距离并标记 `hurtMarked` 同步。
- **后果**：每次滞空最多一次，落地/登出/重生/换维度重置；改高度只改 `DoubleJumpEvents` 的常量。

## D-014 再跃获取与试炼密室限制

- **背景**：需求包含试炼密室（Trial Chambers），但它是 1.21 加入的结构，1.20.1 没有对应 loot table。
- **决定**：再跃获取 = 图书管理员专家 20–32 绿宝石/3 次、满级附魔台 30 档（I）、
  古城/末地城（与远及共享宝箱池，10%/15%，两本书各 50%，I:II = 3:1）；试炼密室暂不实现。
- **后果**：宝箱一箱最多出一本书；升 1.21 或选定 1.20.1 替代结构后再补试炼密室。

## D-015 版本号手动维护，功能新增升 minor

- **背景**：加了两个附魔后 jar 仍是 `0.1.0`；Gradle/Forge 不会自动根据功能改版本。
- **决定**：`gradle.properties` 的 `mod_version` 手动维护；骨架为 `0.1.0`，本次功能新增升到 `0.2.0`。
  jar 名和 `mods.toml` 的 `version` 都由它注入。
- **后果**：以后每次功能/修复都手动改 `mod_version`；产物名随版本变化，旧 jar 由 `clean` 清理。

## D-016 再跃：5 格摔落阈值 + 30% 水平加速

- **背景**：修改再跃：穿戴附魔靴子时摔落受伤高度改为 5 格；二段跳不减速，并获得当前水平速度 30% 的瞬时加速。
- **决定**：服务端 `LivingFallEvent`：距离 <=5 时 `damageMultiplier=0`，>5 时 `distance -= 2`
  （等价于从 5 格开始计算伤害）；二段跳把水平速度乘以 1.30。版本升 `0.2.1`。
- **后果**：所有穿戴再跃靴子的玩家生效，与是否真正使用二段跳无关；
  水平加速是瞬时乘法，之后仍受正常空气阻力。

## D-017 二段跳优先于鞘翅滑翔

- **背景**：同时穿再跃靴子和鞘翅时，原版会在空中按跳跃时发 `START_FALL_FLYING`；需要让二段跳优先，不能滑翔时再滑翔。
- **决定**：客户端检测“空中跳跃且二段跳可用”时先发包，并在该 tick 压掉跳跃键状态，阻止原版起飞；
  服务端如果收到包时已经在 fall flying，则先 `stopFallFlying()` 再执行二段跳。二段跳用掉后不再拦截。
- **后果**：滑翔中按跳跃且本次滞空未用过二段跳，会停滑翔并二段跳；用掉后需松开再按一次跳跃才会滑翔。
  仍保持每次滞空最多一次二段跳。

## D-018 二段跳水平速度由客户端上报

- **背景**：玩家移动是客户端权威的，服务端的 `player.getDeltaMovement()` 在跳跃/空中时常为 0 或滞后；
  之前服务端用它乘 1.30，相当于把水平速度乘成 0，表现为二段跳减速。
- **决定**：`DoubleJumpPacket` 携带客户端当前 x/z；服务端校验有限值、水平速度封顶 1.0 后乘 1.30；
  客户端本地先乘 1.30，保证不等包也立刻有加速。网络协议从 1 升到 2。
- **后果**：客户端与服务端必须同版本；水平加速仍是瞬时乘法，之后按原版空气阻力衰减。

## D-019 每附魔一个 source set + InscribeModule/ServiceLoader

- **背景**：需要按附魔出子集 jar，且保持 `inscribe` modId 和附魔 ID 不变。
- **决定**：远及在 `src/outreach`、再跃在 `src/double_jump`，各自 `DeferredRegister`/事件/网络；
  核心只留 `Inscribe` + `core`。`-Pmodules` 选择 source set；Gradle 生成唯一的
  `META-INF/services/com.hekaijun.inscribe.core.InscribeModule`，由 `ModuleLoader` 发现模块。
- **后果**：子集 jar 只含选中模块的 class；新增附魔要在 `build.gradle` 的 `moduleClasses` 和目录约定里登记。
  不要给单个模块放 service 文件，多个文件会互相覆盖。

## D-020 严格子集，不保留未选中附魔的旧存档

- **背景**：用户确认不管旧存档，只要一个 jar 包含选中的附魔。
- **决定**：子集 jar 完全不注册未选中的附魔；选中的附魔 ID/NBT 保持不变。
- **后果**：未选中附魔的旧书在该 jar 中会失效；需要兼容时用全量 jar，或以后再加占位 stubs。

## D-021 默认只产出一个全量 jar

- **背景**：用户明确不需要把特定附魔单独做成 jar；子集包只是验证模块化构建的临时产物。
- **决定**：默认 `build` 只产出 `inscribe-0.3.0.jar`（全量）；删除 `dist/` 子集包；
  源码模块化保留用于维护，`-Pmodules` 仅作为临时调试能力，不进入常规流程。
- **后果**：不再提供子集分发；如需回退到单体结构，可使用 `backups/0.2.3`。

## D-022 雷击：攻击事件 + 落雷与攻击者短时免伤

- **背景**：雷击只在攻击生物时触发，冷却随等级 6/3/1.5 秒；攻击者站得太近不能被自己的雷击伤到。
- **决定**：`AttackEntityEvent` 只在目标为 `LivingEntity` 时处理；在目标位置生成 `LightningBolt` 并 `setCause`；
  生成成功后给攻击者 10 tick 的雷击伤害免疫窗口，`LivingHurtEvent` 里遇到 `LIGHTNING_BOLT` 且仍在窗口内就取消；
  冷却 120/60/30 tick；宝藏、无附魔台；交易 + 古城/末地城。
- **后果**：非生物目标（含盔甲架）不触发；附近其他生物仍可能被雷击波及；攻击者在窗口内免疫雷击（包括极小概率的自然雷）。

## D-023 迅击：ATTACK_SPEED + 使用时间加速

- **背景**：迅击要同时覆盖剑/斧/三叉戟的攻击间隔，以及弓/弩的拉弓/装填速度。
- **决定**：近战持有时给 `Attributes.ATTACK_SPEED` 加 `MULTIPLY_TOTAL` 0.10/0.20/0.30；
  弓/弩在 `LivingEntityUseItemEvent.Tick` 里按等级累积，额外 `setDuration(getDuration() - 1)`。
  Forge 会把该返回值写回 `useItemRemaining`，所以拉弓/装填会实际变快。
- **后果**：近战缩短攻击冷却、不直接改单次伤害；弓/弩加速是概率式每 10/5/3.3 tick 多减 1 tick；
  附魔台 30 档只出 I 级，II/III 靠交易/宝箱/铁砧；非宝藏。

## D-024 碎甲：斧暴击挂状态 + 攻击者专属穿透

- **背景**：碎甲只在斧暴击时触发，目标必须有护甲；10s 内攻击者所有伤害吃穿透（药水除外）；
  被盾格挡时不触发、不扣冷却，且盾耐久多掉 50%；图标用用户提供的 18×18 PNG。
- **决定**：`CriticalHitEvent` 记录 pending，`ShieldBlockEvent` 优先消费 pending 并额外扣盾耐久；
  `LivingHurtEvent` 挂状态并保存护甲计算前伤害，`LivingDamageEvent` 用 `CombatRules` 计算
  减甲/削韧后的增量伤害；状态存 entity persistent data（10s），冷却 7s；药水按 MAGIC/INDIRECT_MAGIC 排除；
  粒子在 `applySunder` 时发送，客户端用 `SunderParticle` + `particles/sunder.json` + `textures/particle/sunder.png`。
- **后果**：不修改斧子基础伤害，只改攻击者的有效穿透；0 护甲不挂状态；格挡不挂状态/不扣冷却；
  自定义粒子图标的 atlas sprite 名是 `inscribe:sunder`。

## D-025 碎甲修复：铁砧限制 + 图标 atlas/位置

- **背景**：0.6.0 出现图标不显示、斧子劈砍偶发卡顿、碎甲能被上到剑上、图标/中文名需要替换。
- **决定**：新增 `AnvilUpdateEvent` 守卫，非斧/非书目标带碎甲时清空铁砧输出；图标改为用户新给的
  18×18 PNG，位置改到目标头顶 +0.35、尺寸 0.5、不透明度 0.8；移除每 tick 的 pending 清理；
  中文名改“碎甲”，ID 仍为 `inscribe:sunder`。
- **后果**：铁砧/附魔台不能再把碎甲给剑；命令/直接 NBT 仍可绕过；图标 atlas 使用
  `assets/inscribe/particles/sunder.json` + `textures/particle/sunder.png`（sprite 名 `inscribe:sunder`）。

## D-026 碎甲鲁棒性：铁砧守卫 + 背包清理 + 怪物护甲 + SpriteSet

- **背景**：0.6.1 仍被反馈剑可上碎甲、穿甲僵尸无图标/效果、劈斧卡顿；需要按实际玩家/怪物路径重做。
- **决定**：保留 `AnvilUpdateEvent` 守卫，并新增每 20 tick 的玩家背包清理（斧/书以外物品上的碎甲直接移除）；
  护甲判定统一用 `LivingEntity.getArmorValue()`，覆盖穿甲僵尸/怪物，不只玩家；
  粒子改用 `registerSpriteSet` + `SpriteSet`，不再每次创建粒子查 atlas；移除每 tick pending 清理。
- **后果**：旧碎甲剑会在 1 秒内被清理；粒子创建更轻量；新增 `Sunder applied` / `Sunder particle created` /
  `Removed sunder from invalid item` 三条低频日志用于定位。暴击仍是触发前提。

## D-027 铁砧碎甲只允许斧子（收紧左槽）

- **背景**：0.6.2 仍可把碎甲通过铁砧敲到剑上；旧守卫把附魔书也当成合法左槽，书/剑顺序可能绕过。
- **决定**：`AnvilUpdateEvent` 中只要任一侧或输出含碎甲，且**左槽不是 `AxeItem`**，直接清空输出；
  不再允许“书左/剑右”绕过；涉及碎甲时打印 `Anvil sunder check` 日志。
- **后果**：标准“剑左 + 碎甲书右”和反向摆放都不会产出碎甲剑；每秒背包清理仍作为旧物品兜底。

## D-028 铁砧必须取消事件，不能只清空输出

- **背景**：0.6.3 用 `setOutput(EMPTY)` 阻止碎甲剑，但 ForgeHooks 把“空输出”解释为“未处理”，
  返回后原版继续计算，结果仍然把碎甲敲到剑/弓/三叉戟上。
- **决定**：`AnvilUpdateEvent` 是 `@Cancelable`；左槽非斧且涉及碎甲时调用 `setCanceled(true)`，
  ForgeHooks 返回 false，AnvilMenu 直接结束，不再走原版附魔合并。
- **后果**：左槽必须是斧子；书左/剑右也无法绕过；旧物品仍由每秒背包清理兜底。

## D-029 生命汲取：按最终伤害吸血，亡灵/满血跳过

- **背景**：生命汲取需要 20% 吸血、整数向下取整、单次上限 4、满血不触发、亡灵无效、击杀额外回 2，
  并与亡灵杀手冲突；表现是目标身上红色受击粒子。
- **决定**：在 `LivingDamageEvent` 中取攻击者为玩家、主手剑带生命汲取、目标非亡灵、玩家非满血，
  伤害按 `min(event.amount, target.health)` 计算，`heal = min(4, floor(damage * 0.20))`；
  20 tick（1 秒）冷却；`player.heal` 自动封顶；同时发送 `DAMAGE_INDICATOR` 红色粒子。
  击杀在 `LivingDeathEvent` 额外 `heal(2)`；`checkCompatibility` 排除亡灵杀手。
- **后果**：吸血只按护甲/保护后的最终伤害计算；击杀回 2 不占吸血 1 秒冷却；亡灵不触发。

## D-030 所有 Inscribe 附魔统一目标限制

- **背景**：铁砧处理附魔书时会绕过目标物品的 `canEnchant`，导致所有新附魔都能贴到裤子等非法装备；
  之前只给碎甲写了专用守卫，其他五个附魔仍然漏。
- **决定**：新增核心 `EnchantmentRestrictions`：铁砧事件里对所有 `inscribe` 附魔按目标物品
  `canEnchant` 校验，非法组合直接 `setCanceled(true)`；玩家背包每 20 tick 清理一次非法装备上的附魔。
  删除 Sunder 专用铁砧/背包守卫，统一由核心处理。
- **后果**：所有模块必须正确实现 `canEnchant`；附魔书本身仍可持有任意附魔；旧非法装备约 1 秒内被清理。

## D-031 生命汲取只在服务端结算

- **背景**：实测 8 点伤害回了 2 点，存在客户端/服务端各结算一次的可能；同时粒子在胸口容易被模型遮挡。
- **决定**：`LivingDamageEvent` / `LivingDeathEvent` 先判断 `player.level().isClientSide`，只在服务端回血；
  粒子从胸口改到目标头顶上方 0.3 格，并至少发 2 颗 `DAMAGE_INDICATOR`。
- **后果**：回血不会因双端事件叠加；击杀额外回 2 仍是独立奖励，测试 20% 公式时要用非击杀木桩。

## D-032 雷击视觉化：只对目标结算一次

- **背景**：真实闪电是范围伤害并可能附带火焰，10 tick 的 `LIGHTNING_BOLT` 免疫窗口不能覆盖所有情况，
  近距离攻击时攻击者仍可能被自己的雷击/后续火焰伤到。
- **决定**：`LightningBolt.setVisualOnly(true)` 只保留视觉/音效；手动对目标
  `target.hurt(serverLevel.damageSources().lightningBolt(), 5.0F)` 结算一次。删除免疫窗口和
  `LivingHurtEvent` 自伤取消逻辑。
- **后果**：攻击者结构上不会被自己的雷击命中；没有范围伤害/点燃；雷击只作用于主目标。

## D-033 回退 0.7.3 视觉雷击，恢复真实闪电

- **背景**：用户更喜欢真实闪电的视觉冲击，也接受“贴脸可能被范围/火焰误伤”作为玩法风险。
- **决定**：撤销 D-032 的 `setVisualOnly(true)` + 单目标手动伤害，恢复 0.7.2 的真实 `LightningBolt`；
  保留 10 tick 的直接雷击免疫，但范围伤害/点燃仍可能误伤攻击者。0.7.3 归档到 `backups/0.7.3/`。
- **后果**：雷击重新有范围/火焰和误伤风险；全局附魔目标限制、生命汲取服务端结算/粒子等修复不变。

## D-035 熔岩行者：自定义熔岩壳方块

- **背景**：需要把附近岩浆变成临时熔岩壳，内圈常驻、外圈定时恢复，且方块有自定义三阶段贴图、
  石镐及以上固定挖掘时长、无掉落、不进入创造模式。
- **决定**：新增 `lava_walker` 模块和 `lava_shell` 方块（`stage=0/1/2` 对应完整/一级/二级贴图）。
  玩家每 2 tick 扫描：移动时扫描 `min(16, 2+等级)` 范围，静止时只维护 3×3 内圈；外壳方块
  每 30 tick 老化一阶，内圈重置为完整，外圈完整→一级→二级→熔岩（约 4.5 秒）。
  `getDestroyProgress` 只允许石镐及以上并固定 10 tick；`noLootTable` 无掉落；不注册 BlockItem。
  挖掘时由 `BlockEvent.BreakEvent` 处理：玩家移动则恢复壳，静止则变回熔岩。
- **后果**：猪灵堡垒四个表和古城加入战利品；末地城不变；方块只能由效果生成，不能在创造栏获取。

## D-036 熔岩壳反馈修复：生命周期/圆形/透明/静止不补

- **背景**：实测外壳消散太快、移动范围是方形且偏大、常驻范围只有 3×3、破损贴图黑色不透明；
  静止挖壳后 2 tick 内又被补回。
- **决定**：`STAGE_TICKS` 30→60（约 9 秒）；扫描与持久判定统一为半径
  `min(16, 2+等级)` 的圆形；`hasInnerPlayer` 用同半径，所有当前圆内壳持续刷新；
  增加 `noOcclusion`，三个模型加 `render_type: cutout`；玩家 tick 仅在 `blockPosition` 变化时扫描，
  静止时完全不补壳。
- **后果**：静止挖壳后保持熔岩；移动挖壳会恢复；旧壳离开范围后约 9 秒逐级破裂再变熔岩。

## D-037 焚灭：掠夺后的掉落转经验

- **背景**：需要只对 `MobCategory.MONSTER` 的非 BOSS 击杀生效，BOSS/玩家掉落保留，
  怪物死亡经验保留，并且和掠夺叠加。
- **决定**：监听 `LivingDropsEvent`（此时掠夺已结算），检查目标为 MONSTER、非玩家、
  `Tags.EntityTypes.BOSSES` 不含它、掉落非空；击杀者为玩家且手持带焚灭的斧/剑；
  按掉落物总数量乘 5/8/12 给玩家经验，然后清空掉落列表。不监听 `LivingExperienceDropEvent`。
- **后果**：掉落物被经验替代，死亡经验照常；BOSS/玩家/动物/无掉落不受影响；与掠夺兼容。

## D-038 统一获取：战利品箱 + 附魔台

- **背景**：用户要求删除古城/末地城专用获取，改为战利品箱；所有附魔默认进入附魔台。
- **事实核对**：1.20.1 `chests/end_city_treasure` 不含附魔书，排除合理；古城是普通 `chests/*` 表。
- **决定**：`LootInjection` 只处理 `minecraft:chests/*`，排除 `end_city_treasure`，每箱 10% 概率；
  所有模块的 `lootEntries` 不再按表过滤；移除图书管理员交易和钓鱼 2%；
  雷霆/熔岩行者移除宝藏标记并打开附魔台，其余附魔原本已可上附魔台。
- **后果**：42 个 chest 表各注入 20 条书条目；末地城 0 条；所有附魔附魔台可选；
  旧交易/钓鱼不再产出。10% 与“所有 chest 含 spawn_bonus_chest”是本次假设，可按需调整。

## D-039 图书管理员自动交易 + 特殊附魔宝藏

- **背景**：用户要求恢复图书管理员，并让雷击/熔岩行者这类有副作用的特殊附魔回到宝藏、不上附魔台。
- **决定**：新增核心 `InscribeTrades`，4 级图书管理员遍历所有 `inscribe` 命名空间附魔并自动加交易，
  后续新增附魔无需单独写交易。雷击/熔岩行者 `isTreasureOnly=true` 且
  `canApplyAtEnchantingTable=false`；其余附魔仍可上附魔台。战利品箱独立额外出书率从 10% 提到 15%。
- **后果**：特殊附魔只能箱子/交易获得；普通附魔三途径都可用；原版附魔书池不受新增池影响。

## D-040 巨人杀手：最大生命追加伤害

- **背景**：新增剑/斧附魔，命中时按目标最大生命追加伤害，小体型目标封顶，巨型目标不封顶。
- **决定**：监听 `LivingHurtEvent`，仅玩家近战（`getDirectEntity` 为 Player）且主手带附魔；
  按最大生命 1%/1.5%/2% 追加；最大生命 ≤500 时封顶 2/4/8，>500 不封顶。
  阈值用**最大生命**而非当前生命；追加部分参与护甲/抗性结算。
- **后果**：无冷却/冲突；对高血量目标收益线性增长；不是真实伤害。

## D-041 巨人杀手 >500 真伤化

- **背景**：巨人杀手对 >500 最大生命目标不封顶，但追加部分仍被护甲减免；用户要求该部分无视护甲。
- **决定**：`≤500` 继续在 `LivingHurtEvent` 加、参与护甲；`>500` 改在 `LivingDamageEvent` 加，
  此时护甲/保护/伤害吸收已结算，追加部分绕过这些减伤，基本等同真实伤害。
- **后果**：高血量目标收益不受护甲影响；低血量目标保持原结算；无冷却/冲突不变。

## D-042 版本号规则：末位递增、满10进位

- **背景**：用户要求下一个版本为 1.0.0，之后每次新增附魔/修改只动最后一位。
- **决定**：基线 1.0.0；改动按 1.0.1、1.0.2 … 递增；1.0.9 后进位为 1.1.0，
  1.1.9 后为 1.2.0。正常不单独改第二/第三位，只有末位满 10 才进位。
- **后果**：每次发布版本号可预测；功能与 0.9.4 相同，1.0.0 仅作为新基线。

## D-043 无伤：10 秒充能的一次免伤护盾

- **背景**：胸甲附魔，10 秒未受伤获得护盾，带攻击者的伤害变 1；任何伤害重置计时。
- **决定**：用 `LivingDamageEvent` 记录实际伤害时间和护盾状态；任意实际伤害重置 10 秒计时；
  满 10 秒获得护盾；带攻击者且伤害 >1 时改为 1 并消耗护盾；无攻击者伤害不消耗但重置计时。
  护盾存在期间一直保留，消耗后重新充能 10 秒。
- **后果**：摔伤/火焰/溺水不会触发减伤，但会打断充能；箭矢/近战/火球等 `getEntity()` 非空的伤害会触发。

## D-044 无伤护盾：任何伤害都消耗

- **背景**：实测持有护盾时先受环境伤害、再受有攻击者伤害，仍会触发 1 点减伤；原因是环境伤害只重置计时未移除护盾。
- **决定**：护盾存在时，任何实际伤害都移除护盾；若该伤害有攻击者且 >1，则先变 1；无攻击者伤害不触发减伤但同样破盾。
- **后果**：摔伤/火焰/溺水会破盾并重置 10 秒；之后的有攻击者伤害正常结算，需重新充能。

## D-045 焚灭经验审计 + 生命汲取 HUD 抖动

- **焚灭审计**：`LivingDropsEvent` 每次死亡只触发一次，服务端才结算，不存在重复发经验；
  只有在“玩家击杀 + MONSTER + 非 BOSS + 有掉落”时转换。经验跳变来自原版等级曲线
  （低等级 7/9/11 点即可升级）与按物品数量结算。数值按需求降为 3/5/8。
- **生命汲取抖动**：新增 `InscribeNetwork` S2C 包；吸血/击杀回复后发 `ShakeHealthPacket`，
  客户端通过反射设置原版 `Gui.healthBlinkTime = guiTicks + 20`，复用原版心形抖动。
  生产环境字段名混淆时回退扫描小数值 long 字段。
- **后果**：无新方块/物品；HUD 效果只在客户端；专用服务器不加载客户端类。

## D-046 生命汲取范围与抖动兜底、焚灭再降

- **范围**：生命汲取不再排除所有亡灵，只排除 `EntityTypeTags.SKELETONS`；僵尸、凋灵、幻翼等
  非骷髅亡灵可吸血/击杀回复，骷髅/流浪者/凋灵骷髅不行。
- **抖动**：保留 S2C `healthBlinkTime` 包，同时新增客户端 tick 兜底：手持生命汲取且生命值上升
  时触发原版心形抖动；抖动时长采用原版治疗档 `tickCount + 10`。开发名 `healthBlinkTime`，
  生产 SRG 名 `f_92976_`，显式按两个名字取字段，避免回退选到 `lastHealthTime`。
- **焚灭**：每掉落物 2/4/6；核对 `LivingDropsEvent` 无重复发放。
- **后果**：客户端兜底可能让“手持生命汲取时的其他治疗”也触发抖动，但保证吸血可见。

## D-047 解除生命汲取与亡灵杀手互斥

- **背景**：生命汲取已改为只排除骷髅类，不再有亡灵限制；用户要求解除与亡灵杀手的互斥。
- **决定**：删除 `LifeSiphonEnchantment.checkCompatibility` 中对 `Enchantments.SMITE` 的判断，
  保留其他原版兼容性逻辑（基类默认）。
- **后果**：生命汲取与亡灵杀手可同时附魔；对亡灵/非亡灵按各自规则结算。

## D-048 冰棘：单图标合并减速/挖掘疲劳

- **背景**：需要新增护甲附魔，受击概率给攻击者一个“冰棘”效果，同时表现减速和挖掘疲劳，
  但 HUD/背包只显示一个效果图标。
- **决定**：注册自定义 `MobEffect` `inscribe:frost_thorns`；`LivingTickEvent` 动态给效果持有者
  添加移动速度/攻击速度属性修饰；`PlayerEvent.BreakSpeed` 按 0.3^(挖掘等级+1) 降低挖掘速度。
  不额外施加原版挖掘疲劳，保证只显示一个图标。`addEffect` 处理负面免疫。
- **触发**：`LivingAttackEvent`（在 `isInvulnerableTo` 之前）触发，因此无敌/高减伤仍可施加。
- **数值**：玩家/非玩家分别按设计表；概率 15/30/45%，无冷却。

## D-049 冰棘概率调整

- **背景**：用户认为冰棘触发率偏低，要求按攻击者类型拆分概率。
- **决定**：`chance(level, player)`：非玩家 40/60/90%，玩家 20/35/50%；
  其余数值（减速、挖掘疲劳、时长、无冷却）不变。
- **后果**：非玩家攻击时明显更稳定触发；玩家 PvP 仍保留较低概率。

## D-050 斩首：LivingDropsEvent 头颅掉落

- **背景**：斧专属附魔，玩家亲手击杀指定原版生物时掉头；玩家头需要击杀者皮肤。
- **决定**：`LivingDropsEvent` 中检查直接伤害来源为玩家、主手为斧、带斩首；只映射僵尸、骷髅、
  凋灵骷髅、苦力怕、末影龙、玩家六种。玩家头用 `NbtUtils.writeGameProfile` 写入击杀者
  `SkullOwner`。宝藏、不进附魔台，与焚灭按注册名互斥。
- **后果**：箭/火焰/宠物/摔落不触发；其他生物不掉头；头颅必掉，不受抢夺影响。

## D-051 铁砧成本线性化与20条上限

- **背景**：原版 `RepairCost` 每次操作翻倍，11 次后出现千级经验和“过于昂贵”；需要上限20条。
- **决定**：新增 `AnvilCostRules`。书+装备由本模组接管合并：最多20条，成本 `1 + 新增/升级条目×2`
  （重命名+1），含 `inscribe` 附魔时 `ceil(cost×0.7)`，上限39。所有操作前把 RepairCost 封顶5；
  装备+装备/修理仍走原版，只做封顶。
- **后果**：书+装备不再出现“过于昂贵”；成本线性可预期；装备互合/修理仍可能受原版成本影响。

## D-052 铁砧低位原版 + 高位线性（弃用1.0.9）

- **问题**：1.0.9 的成本公式 `1+条目×2` 把所有操作压成3；1.1.0 初版又接管了低位，导致第一次附魔就20/30级。
- **决定**：`AnvilUpdateEvent` 只在“词条数≥10 或基础成本≥30”时接管书+装备输出/成本：
  成本 `41 + 4×(词条数-10)`，无39上限；20条封顶；整本书全为inscribe才 `ceil(cost×0.7)`。
  低位完全返回，让原版计算；客户端只隐藏成本≥40时的“过于昂贵”文字。不使用 Mixin。
- **后果**：第一次/少量附魔保持原版；高位继续线性上涨且不再被40级截断；装备+装备/修理仍原版。

## D-053 删除经验减免并修复成本底框

- **背景**：1.1.0 的30%减免只对纯inscribe书生效，用户要求完全删除；同时客户端覆盖层用浅灰底覆盖了原版成本深色底框。
- **决定**：`AnvilCostRules` 对所有书统一按41/45/49…计费，不再判断书是否纯inscribe；`AnvilCostOverlay`
  先以不透明GUI底色擦掉原“过于昂贵”，再用原版 `0x4F000000` 深色画成本框并写文字。
- **后果**：纯/混合书成本一致；成本≥40时视觉恢复原版深色底板。

## D-054 修复同ID附魔重复

- **背景**：高位铁砧用 `ItemStack.enchant` 升级时向 NBT 追加条目，旧等级没有被替换，导致同ID附魔重复。
- **决定**：合并在 Map 中完成，最后用 `EnchantmentHelper.setEnchantments` 重写整张附魔表；
  同等级/更低等级的书直接取消，不再进入原版或追加。
- **后果**：锋利5 打锋利5 无输出；锋利4→5 只保留5；20条上限与线性成本不变。

## D-055 成本框宽度修复

- **背景**：深色底框按 `max(新成本宽度, 原“过于昂贵”宽度)` 绘制，导致左边过长。
- **决定**：擦除旧文字仍使用最大宽度，但深色框只按新成本文本宽度绘制。
- **后果**：保留原版深色底框，同时不会出现左侧过长空白。

## D-056 高位成本按操作次数递增

- **背景**：此前成本按词条数计算，升级已有词条时词条数不变，导致连续显示41。
- **决定**：物品NBT `inscribe_anvil_high_step` 记录高位操作次数；首次41，之后每成功一次+4。
  升级/新增都递增；同等级书取消，不消耗次数；20条上限不变。
- **后果**：高位成本稳定为41、45、49、53…，不再因升级词条卡住。

## D-057 双多词条物品合并的成本框修复

- **背景**：两个多词条物品合并时成本可能远高于“过于昂贵”文本宽度，只按旧文本宽度擦除会残留左侧深色底。
- **决定**：成本行从 `left+8` 到右侧整行用不透明GUI底色擦除，再只按新成本文本宽度绘制深色框。
- **后果**：双多词条物品/普通书合并均不会出现左侧过长或残留底框。

## D-058 追猎：buff层数同步与无倒计时

- **背景**：需要把追猎层数显示为名为“追猎”的buff，等级同步层数，不显示剩余时间；3层以上持续红色环绕粒子；miss/转火清零。
- **决定**：服务端 Map 维护目标/层数/到期时间，伤害在 `LivingHurtEvent` 按层加算；buff 使用无限时长
  `MobEffectInstance`（amplifier=stacks-1），因此HUD不显示倒计时；4秒由服务端 tick 删除。
  miss通过客户端 `LeftClickEmpty` 发包，转火/死亡/退出清零；3层以上服务器发送红色尘埃粒子。
- **后果**：图标等级与层数一致；无倒计时；PvP 伤害减半；不与现有附魔冲突。
